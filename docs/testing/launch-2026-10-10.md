# Luma Green Launch Test Plan

> Status: approved work plan; test execution pending. Prepared 6 October 2026.
> Target decision: Saturday 10 October 2026, Asia/Kolkata.
> Owners: founder, test lead and engineer. Assign named people before the first run.

This plan covers the accounts, roles, material chain, payment boundaries and
release checks for the requested Luma.Green launch. Launch only the scope that
has complete test evidence and working required providers. Saturday is a target,
not a promise that the full platform or external approvals will be ready.
Keep each incomplete flow in the result log as BLOCKED or NOT RUN. Do not remove
it from the plan to obtain a pass. The founder must explicitly accept any
smaller release scope and its visible limitations.

The engineer may continue the approved implementation without another plan
approval. This document does not report completed acceptance tests. The approved
normal-user methods are verified email/password and phone OTP. All development
verification and disposable accounts in this test pass must remain local.

## 3 Environments and safe test data

**L0 — local disconnected and unit tests.** Use empty configuration and isolated
fixtures to test validation, loading and unavailable states. These tests do not
prove authentication, persistence or external delivery.

**L1 — local connected acceptance.** Use a local frontend and the isolated local
Convex process. Record exact origins, ports, candidate SHA and seed version.
Use Better Auth's real HTTP handler and Convex adapter. Verify session reload,
component persistence after restart and private file storage before the role run.
Keep Resend, MSG91, gateway and other live provider keys absent. Inspect network
requests and local delivery records to prove no SMS or email leaves the machine.
No cloud development fallback is authorized for disposable auth tests. If local
components fail, fix or record the blocker and bring the decision to the founder.

**P1 — provider sandbox.** This is a later, separate gate. Use provider sandbox
accounts, controlled destinations and explicit authorization for external sends.
Do not expose the local development challenge service through a public tunnel.
A gateway may require a separately approved test deployment for public webhooks.
Sandbox transactions do not prove live settlement or merchant approval.

**P2 — production smoke.** Use the final approved release and live configuration
only after the release decision. No synthetic local identity, test sender,
fixed challenge, seed function or dev flag may cross into production. Use
controlled operator accounts and minimize side effects.

Use reserved `.test` email addresses for L1 and synthetic phone fixtures which
cannot reach a real subscriber through the local delivery path. Use fabricated
names, sites, material records and scrubbed documents. Never copy customer data.
Do not use image GPS as a location source. Store exact grams and paise; keep test
prices visibly labelled. Use a seed run ID and record aliases instead of live IDs.

Create identities through supported auth flows. Create domain data through
validated APIs or narrow local-only fixture functions. Prove that the seed
refuses cloud targets, is repeatable without duplicates and removes only its
own records. Test cleanup with a preserved unrelated local record.

Generate a unique strong password for each email test account. Keep passwords
and access procedures only in the restricted annex or password manager, outside
Git and outside the shared guide. The annex records account alias, local origin,
workspace, role, expected first screen, custodian and expiry/rotation date.
Phone and TOTP rows describe the private access procedure. Do not print their
codes, seeds or backup codes. Revoke test sessions and delete the local fixtures
when the acceptance run ends.

is missing, record BLOCKED. Do not substitute an administrator session.

| Fibre, textile and garment manufacturers                           | Separate subtype journeys; confirm actual screens and evidence fields. Do not invent missing transformations.                        |

| Negative and multi-workspace fixtures                              | Unapproved/suspended organization, wrong-material buyer, outside user, revoked user and a person in two organizations.               |

For each organization/workspace group, exercise owner, admin, member and viewer
with the same records. Where a role is not applicable, state why in the signed
permission matrix; the role name alone is not permission. The engineer and test
lead must record, per capability, ALLOW or DENY for invite, revoke, role change,
price read, price edit, inventory write, trade approval, quality write, report
read, export and private-file read. Founder resolves any unapproved row before
that workflow is enabled.

The acceptance baseline is least privilege: only an owner or explicitly
permitted admin manages invitations; members act only within assigned duties;
viewers cannot write; observers receive only their explicit data grant. Reject
cross-organization reads and writes for every role, including role-management
requests. Test removal/demotion of the last owner against the approved rule.

## 5 Authentication and workspace cases

Record L1 browser evidence and automated handler/adapter evidence separately.
For each case, include reload or a fresh request to prove server behavior.

- **AUTH-01:** Sign up by email/password. Before verification, attempt private
  access and expect denial. Use the local-only verification message, verify,
  log in, reload and confirm the correct account. Sign out and confirm private
  reads and browser Back cannot recover a live session.
- **AUTH-02:** Repeat with phone OTP. Reject malformed, wrong, expired and used
  codes. Test resend delay and server rate limits across two browser profiles.
  Provider failure must not create a session or trigger an automatic send loop.
- **AUTH-03:** Try duplicate email, duplicate phone, wrong password, unknown
  email and normalization variants. Prevent account enumeration and silent
  account merging. Linking email and phone requires proof of both identifiers.
- **AUTH-04:** Request email password reset, use a valid local link, then repeat
  it and use an expired/tampered link. Only the valid one-use link works. Confirm
  the new password and the documented session revocation policy. A phone-only
  account must not gain a password through an unverified reset path.
- **AUTH-05:** Enable optional user TOTP; test valid, invalid and expired code,
  one-use recovery code, removal and sign-in with a remembered/stale tab. No
  session becomes usable before all required factors pass.
- **AUTH-06:** Set up the configured platform admin with the private setup
  token. Require password plus TOTP. Reject another email, repeated setup and
  ordinary-user recovery attempts on the admin. Admin reset preserves required
  TOTP. Remove the setup token after setup; keep all secrets out of captures.
- **AUTH-07:** Force sign-out failure and retry. Confirm active account state is
  honest. Revoke push/device bindings before sign-out completes. Late provider
  or session responses cannot restore the old account or its subscriptions.
- **AUTH-08:** Try the local verification mechanism with a production origin,
  cloud target, browser-only switch and missing server guard. All must fail.
  Inspect console, logs and responses for leaked passwords, tokens or codes.
- **TEAM-01:** Owner invites a new verified email for each permitted role. The
  recipient sees the organization and role before accepting. Verify exactly one
  membership, correct first screen and an audit event.
- **TEAM-02:** Invite an existing user and a phone-only user. The phone-only
  user must verify the invited email first; typed email alone grants nothing.
  A different verified email cannot accept. Check safe return URLs.
- **TEAM-03:** Expire, revoke and reuse invites. Reject each invalid attempt;
  two tabs accepting the same invite must produce one grant. Repeated send and
  acceptance failures must not create duplicate memberships or audit grants.
- **TEAM-04:** Switch between two workspaces. Confirm current permissions and
  data every time. Changing a URL, record ID or request payload cannot escape
  the chosen organization. Test reads, writes, exports and private files.
- **TEAM-05:** Revoke/demote a member while their second browser has a screen
  open. The next server operation and live subscription must reflect current
  access. Concurrent role updates cannot restore a removed role from stale data.
- **TEAM-06:** Repeat each role's allowed and denied actions from section 4.
  Test last-owner protection, unauthorized invites and self-promotion. Confirm
  every grant, revoke and role change has actor, time and target in the audit.

## 6 Household and work cases

- **REC-01:** Household creates a pickup through manual material entry, with
  browser location allowed and denied. Retain an editable address. A photo is
  optional; neither AI nor photo metadata may invent confirmed location/mass.
- **REC-02:** Verify phone/email as required, quote, booking, tracking,
  cancellation and duplicate submission. Decline or time out the first shop
  offer, then confirm the documented next assignment. Reload after each state.
- **REC-03:** Kabadiwala records actual material and weight, shows the receipt
  to the household, and records direct cash/UPI payment. Confirm stock, points
  and audit entries occur once. Luma must not report a gateway transfer.
- **REC-04:** Test 1 g, 1,001 g, fractional locale entry, zero, negative, NaN,
  unsafe integer and an unsafe product. For 1,001 g at 12,300 paise/kg, the
  accepted rounding contract must give 12,312 paise. Confirm shared exact-money
  helper behavior; reject unsafe totals before mutation. Display locale digits.
- **REC-05:** Wrong household, wrong shop and revoked staff try tracking edits,
  receipt changes and file reads. Designed public tracking reveals only its
  allowed view and never grants cancellation or private-record rights.
- **REC-06:** Repeat after network loss immediately before/after save. Read the
  committed result before retry. No double receipt, stock, points or payment
  record. Retain the user's draft after a confirmed failed save.
- **WORK-01:** Saathi browses permitted jobs, takes one, completes their own
  eligible job and views earned amounts. Reject future/other-user completion.
  Two workers competing for one job must produce one assignee; repeat completion
  changes nothing. Do not imply that an earnings record paid the worker.

## 7 Business material and PET cases

Use one labelled PET chain with measured input, output, loss and separate side
streams. Record evidence per handoff. Run each supported screen with its proper
buyer/seller account. Mark a missing transformation or integration BLOCKED.

- **PET-01:** Record source and origin for household, generator site and
  manufacturer byproduct. Preserve site, actor, material, time and lot link.
  Declared origin and photo evidence do not prove regulatory clearance.
- **PET-02:** Household to kabadiwala, kabadiwala to preprocessor, preprocessor
  to recycler, and recycler to manufacturer each need dispatch/receipt actors,
  measured grams, custody events, supporting files and a discrepancy path.
  No handoff can silently edit its predecessor's measurement.
- **PET-03:** Test received bottles/bales, PET flakes and supported output
  forms. Separate caps/rings, labels, contamination and rejects. Check input
  equals accepted output plus recorded loss/side streams, with the approved
  tolerance. The workbook's illustrative yield is not an accepted rule.
- **PET-04:** Record sample/inspection method, quality grade, accept/reject,
  correction reason, actor and date. An amended result retains its history.
  Require authorized reviewer actions; do not overwrite evidence or auto-accept
  a lot from a seller claim. Undefined quality limits block that quality gate.
- **PET-05:** Manufacturer lists a non-hazardous byproduct. Allow an approved
  buyer handling that material regardless of the old next-role restriction.
  Deny unapproved, suspended, wrong-material and self-purchase attempts. Hold
  hazardous/uncertain materials for the separate approved eligibility process.
- **PET-06:** Two buyers request more than available grams. Accept and retry
  concurrently; free/reserved stock stays consistent and non-negative. Decline,
  cancel, withdraw and failed dispatch follow their exact release rules.
- **PET-07:** Attach quote, order, invoice, transport and official certificate
  references. Access is scoped; a reference cannot mint a certificate, create
  stock, prove payment or grant regulatory approval. Test duplicates and changes.
- **PET-08:** Missing gateway blocks payment-dependent dispatch/settlement and
  completion. Calling old demo-pay actions, editing requests or uploading payment
  proof cannot mark B2B paid. Preserve an honest blocked message and no extra
  stock movement. This passes the safety boundary, not a completed B2B trade.
- **PET-09:** After provider integration, run sandbox order, payment, verified
  webhook, dispatch, receipt, refund and settlement reconciliation. Reject forged
  signature, wrong amount/currency/order, replay, duplicate, delayed and reversed
  webhook order. Do not lose money/stock on timeout or retry. P1 stays BLOCKED
  until the provider and integration exist; P2 needs separate live evidence.

## 8 Observers files reports and failure cases

- **OBS-01:** For city, CSR, lender, auditor, union and brand accounts, approve
  account access, then test before/after a specific data grant. Approval alone
  must expose no private prices, stock, identities or certificates. Revoke the
  grant while the report is open and recheck server read/export denial.
- **OBS-02:** Compare reports with the permitted source records and period.
  Show zero, partial and unavailable states honestly. No synthetic live prices,
  impact statistics, issued credits or undisclosed cross-organization totals.
  Keep recorded evidence separate from verified external outcomes.
- **FILE-01:** Upload a valid image/PDF and invalid type, oversized, zero-byte
  and corrupt file. Interrupt upload and retry. Confirm size/type validation,
  clear errors, no unintended duplicate link and scoped orphan cleanup.
- **FILE-02:** Read/download as owner, permitted teammate, viewer, outsider,
  revoked member and signed-out person. Check non-cacheable private responses;
  copied storage URLs must not bypass access. Inspect metadata/privacy treatment
  for supported image formats. Never use embedded GPS to assign a location.
- **FAIL-01:** Test slow/offline network, server failure, 401/403, 429 and provider
  timeout. Loading must not show false zero/success. Keep recoverable drafts,
  prevent duplicate clicks, bound retries and recheck state after reconnection.
- **FAIL-02:** Rapidly switch accounts/workspaces while requests/uploads run.
  Old responses cannot appear in the new account or write to the wrong org.
  Refresh mid-flow and open two tabs to expose stale status and session races.
- **API-01:** Where industry API access is enabled, test scoped key creation,
  expiry, revocation, quota and cross-org denial. Return exact grams/paise and
  current membership. Do not expose keys in screenshots or shared logs.
- **AUDIT-01:** Match each domain state change to its audit event, actor, target
  and reason where required. Replays do not duplicate commercial effects.
  Changing an emission factor must not restate an already-issued credit.

## 11 Result log and release rules

Use one result per case, role and evidence level. Allowed states: NOT RUN,
PASS, FAIL, BLOCKED and NOT APPLICABLE with a signed reason. A blocked required
case has the same release effect as a failed required case. Retain failures and
retest links; do not replace the first result with a green screenshot.

Copy this record for each run:

| Field                   | Record                                                                                                  |
| ----------------------- | ------------------------------------------------------------------------------------------------------- |
| Run and case            | Run ID; case ID; date/time in Asia/Kolkata; tester name.                                                |
| Build and environment   | Commit SHA; L0/L1/P1/P2; app/backend origin; schema and seed version.                                   |
| Identity and permission | Synthetic account alias; org/workspace alias; role; approved capability row.                            |
| Preconditions and steps | Seed facts; exact input grams/paise; reproducible steps.                                                |
| Expected and actual     | Required behavior; observed behavior; resulting record/audit aliases.                                   |
| Result and evidence     | State; screenshot/trace/log path; command exit result; redacted provider event reference if applicable. |
| Defect and retest       | Defect ID; P0/P1/P2/P3; owner; fix SHA; retest result; regression impact.                               |
| Blocker                 | Missing code, provider, permission decision or access; owner; next action; target date.                 |

Severity rules: **P0** includes account takeover, cross-organization disclosure,
secret leak, incorrect money/stock or irreversible data loss. **P1** includes a
broken required signup, permission, invite, material or payment workflow.
**P2** is a limited defect with a safe documented workaround; **P3** is cosmetic.
P0 and P1 block release. A founder waiver cannot make a failed security or money
check pass; hold or explicitly remove that capability from the proposed release
and retest its disabled boundary. Record any accepted P2/P3 with owner and due date.

Release requires all of the following:

1. Named scope and role/permission matrix, with every required case passed at
   the required evidence level. No required NOT RUN or BLOCKED rows.
2. Current `pnpm check`, formatting, `pnpm build`, affected e2e and complete
   required hosted checks passed on the exact candidate. Run `pnpm apps:check`
   and native release gates for any native scope. Do not reuse old test totals.
3. Zero open P0/P1 issues; engineer and test lead sign the defect report.
4. Required Resend/MSG91 delivery and gateway gates passed for each advertised
   production capability. Sandbox evidence does not satisfy live verification. Missing gateway means the full
   B2B payment release is blocked and must remain visible in the launch decision.
5. Current guide source, real browser captures, build record and Word guide
   agree. Inspect every rendered page. Update the existing Google Doc ID from
   `docs/user-guide/cloud.json` in place and verify its sharing. No passwords in
   the shared guide. Record any connection gate explicitly.
6. Backup/recovery points, deployment sequence, operator coverage and a tested
   rollback procedure recorded. Founder signs GO or NO GO with date and scope.

## 12 Release smoke test and rollback

Before release, record the known-good frontend deployment and backend/schema
revision, export backup, secret configuration owner and recovery procedure.
The pre-reset prototype exports are historical recovery points, not a safe
schema rollback target for new accounts. Rehearse restore locally first.

Deploy the validated backend and auth component before its matching frontend,
using the checked release path. Confirm the target deployment before any
command. Preserve cloud pause until the release owner explicitly reactivates it.
After deployment, check HTTPS/domain, health, public loading/unavailable states,
verified signup/login, own workspace, a denied cross-org request, invite/revoke,
private file access, sign-out and one authorized non-destructive material flow.
Check audit events and console/network again. Test production email/SMS with
controlled recipients. Perform a live payment/refund only after explicit
provider readiness and founder authorization; otherwise keep that flow blocked.

If a P0/P1 appears, stop launch and affected writes/sends, preserve redacted
incident evidence and notify the founder/test lead. Disable the affected feature
or serve the agreed unavailable state. Restore the known-good frontend only if
its backend contract is compatible. Prefer a verified server fix for incompatible
schema changes; do not blindly redeploy the pre-reset backend or delete new data.
Use backup restore only through the incident owner and reviewed recovery plan.
After recovery, repeat the smoke test and every affected case before reopening.
